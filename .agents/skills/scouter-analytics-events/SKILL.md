# Scouter 분석 이벤트

Scouter의 기존 분석 클라이언트와 토큰 설정을 재사용해 요청받은 화면의 이벤트만 점진적으로 추가한다. 한 작업에서 요청받지 않은 다른 화면까지 확장하지 않는다.

## 작업 순서

1. 이벤트 명세와 대상 화면의 실제 사용자 흐름을 확인한다.
2. 현재 API Zod 스키마, fetcher와 컴포넌트 호출부를 함께 읽어 각 프로퍼티의 출처를 확인한다.
3. 기존 분석 클라이언트와 화면 주변의 이벤트 패턴을 확인하고 중복 구현을 피한다.
4. 이벤트 이름, 실제 발생 조건, 프로퍼티와 데이터 출처를 확정한 뒤 구현한다.

## 이벤트와 프로퍼티 계약

- 이벤트와 프로퍼티는 `snake_case`를 사용하고 타입으로 허용 조합을 제한한다.
- 각 이벤트 이름 위에 사용자가 어떤 동작을 했을 때 발생하는지 설명하는 주석을 작성한다.
- API의 ID, enum과 boolean은 별도 표시값으로 재가공하지 않고 그대로 기록한다. 타입도 가능한 한 API 스키마에서 파생한다.
- 화면 공통 프로퍼티와 중복되거나 여러 API 값을 조합해 추정해야 하는 프로퍼티는 추가하지 않는다.
- 현재 API 계약으로 확인할 수 없는 필드는 구현하지 않고 후속 수정사항으로 남긴다.
- 별도 분석 요구가 없다면 화면 방문이나 편집 세션을 구분하기 위한 추가 식별자를 만들지 않는다.

## 발생 시점

- 클릭 이벤트는 사용자가 실제 동작을 실행한 시점에 기록한다.
- 완료 이벤트는 mutation 또는 API 요청의 성공이 확인된 뒤에만 기록한다. 요청 시도나 낙관적 상태 변경을 성공으로 취급하지 않는다.
- 동일한 사용자 동작을 설명하는 이벤트를 중복 발생시키지 않는다.
- 연속 입력값을 키 입력마다 추적하지 않는다. 수정 여부보다 제출 결과가 목적이면 제출 시도와 성공 이벤트를 사용한다.
- 정책 오류 이벤트는 사용자가 실제로 본 폼 검증 또는 정책 차단에만 사용한다. API와 네트워크 장애는 제품 분석 이벤트에 섞지 않는다.

## 화면 구조

- 여러 하위 컴포넌트가 같은 화면 공통 프로퍼티를 필요로 하면 라우트가 Context Provider와 추적 함수를 소유한다.
- 분석을 위해 기존 JSX 구조를 별도 페이지 컴포넌트로 감싸거나 불필요한 wrapper를 만들지 않는다.
- 화면별 이벤트 이름과 프로퍼티 타입은 기능 가까이에 모으고, 하위 컴포넌트는 Context에서 타입이 지정된 추적 함수를 사용한다.
- 프로퍼티가 없는 이벤트도 같은 타입 계약을 거쳐 호출한다.

## 범위 경계

- Mixpanel 패키지, 초기화 옵션, 토큰 환경 변수와 사용자 식별 설정은 이벤트 작업에 필요하다는 이유만으로 변경하지 않는다.
- API에 필요한 정보가 추가되기 전까지 임시 파생값이나 placeholder 프로퍼티를 만들지 않는다.
